# B Review — Pass 1

1. [`ensure_replicated_call_site.md`, ~line 92, factual error in replay mechanism, fix description]
   The Note states: "On replay, the tensor is still sharded (same input), so `_ensure_replicated` would again call `ttnn.from_torch` — but this time inside a replay, where the new buffer's address differs from the one recorded at capture."
   This is wrong. As established in `what_trace_records.md` (lines 25–30), replay does **not** re-execute the Python forward pass. `_ensure_replicated` is not called during replay at all; no Python runs. The actual failure mode is that the DMA command recorded at capture references the address of a buffer that was allocated transiently during capture and no longer holds valid data (or may be recycled for a different purpose) on replay. Implementing the described mental model — that `from_torch` is re-called during replay — would give a reader a fundamentally wrong picture of why the bug occurs and could mislead them about which replay-time invariants matter.
   Fix: Replace the Note with the correct mechanism: during replay, the recorded command buffer issues a DMA or kernel-dispatch command to the address that `from_torch` produced during capture. That buffer may have been freed or reused between the capture run and replay, so the address is stale. Python never re-executes; there is no second `from_torch` call during replay.

2. [`ensure_replicated_call_site.md`, ~lines 138–145, incorrect fix — `ttnn.copy` cannot accept a host-resident source tensor]
   The proposed fix creates `cos_host = ttnn.from_torch(cos_torch, dtype=..., layout=...,)` with no `device=` argument, yielding a host-resident `ttnn.Tensor`, then calls `ttnn.copy(src=cos_host, dst=self.cos_replicated)`. `ttnn.copy` operates between two device-resident tensors; it enqueues a device-side DMA command. Passing a host-resident tensor as `src` is not a supported usage and would raise an error or silently misbehave. The correct trace-safe approach is to call `ttnn.from_torch` with `device=self.mesh_device` targeting `self.cos_replicated` directly (i.e., use an `output_tensor=` or equivalent in-place argument if the API supports it), or to perform the host-to-device transfer using the TTNN API that writes into an existing device buffer. A reader implementing the code as written will not produce working software.

3. [`ensure_replicated_call_site.md`, ~line 39, wrong variable name in call-chain diagram]
   The capture-bracket diagram shows `ttnn.from_torch(cos_replicated, device=mesh_device)`, using `cos_replicated` as the first argument. The actual implementation shown at lines 72–83 passes `tensor_torch` (the gathered host tensor) as the first argument. `cos_replicated` is not in scope at that point and is the name reserved for the pre-allocated fix buffer introduced later in the file. A reader tracing through the diagram alongside the implementation will see a mismatch and may incorrectly conclude the diagram is showing the post-fix code path.
   Fix: Change `cos_replicated` in the diagram to `cos_torch` (or `tensor_torch`) to match the implementation.

4. [`ensure_replicated_call_site.md`, ~line 60, formula does not match standard rotary embedding definition]
   The rotation formula is written as:
   $$q'_i = q_i \cos(\theta_i) - q_{i+d/2} \sin(\theta_i)$$
   In the standard RoPE formulation (Su et al. 2023), the paired index is $i + d/2$ only when the rotation pairs are arranged in the "GPT-NeoX" interleaved style. Qwen3 uses the non-interleaved (consecutive-pairs) convention where odd index $2k+1$ pairs with even index $2k$, so the formula should show $q_{2k}$ and $q_{2k+1}$ as the paired components, not $q_i$ and $q_{i+d/2}$. As written, a reader implementing the kernel pairing logic would use the wrong index offset and produce numerically incorrect outputs.
   Fix: Replace with the paired form $q'_{2k} = q_{2k}\cos(\theta_k) - q_{2k+1}\sin(\theta_k)$, or explicitly state which indexing convention Qwen3 uses and cite the source.

5. [`ensure_replicated_call_site.md`, ~line 92, note claims conditionality "does not help with trace safety" for the wrong stated reason]
   This is a corollary of issue 1 above: the note argues the conditional branch re-executes on replay, which is false. The correct reason conditionality does not help is that the trace records whatever happened during the capture run — including the transient buffer address — regardless of whether the branch would be taken again. The note's conclusion ("the addresses diverge, and the invariant is violated") is right, but the stated causal chain is wrong. A reader relying on this explanation to reason about other conditional trace-unsafe operations would apply an incorrect mental model.
   Fix: Correct the mechanism to match issue 1's fix: the conditionality is irrelevant because replay does not re-execute Python; the problem is purely that a transient address was baked into the command buffer at capture time.

1. [`ensure_replicated_call_site.md`, ~lines 144–153, the proposed fix still calls `ttnn.from_torch` with `device=` inside the capture bracket, which allocates a new device buffer and therefore still breaks trace]
   The corrected fix code (lines 144–153) introduces `cos_device = ttnn.from_torch(cos_torch, ..., device=self.mesh_device, mesh_mapper=ReplicateTensorToMesh(...), ...)` inside `forward`, then calls `ttnn.copy(cos_device, self.cos_replicated)`. The `ttnn.from_torch(..., device=self.mesh_device)` call allocates a new device buffer for `cos_device` on every invocation — as established in `from_torch_is_a_host_operation.md` lines 20–37, every call to `ttnn.from_torch` with `device=` runs the device memory allocator and returns a fresh DRAM region. This allocation occurs inside the capture bracket (inside `forward`), so the address of `cos_device` is baked into the DMA command that `ttnn.copy` enqueues. On replay, `cos_device` is not re-allocated; that baked address is stale. The guide's own Key Finding at line 163 claims the fix "separates the host work from the device buffer allocation," but the code does not achieve this separation: `from_torch` with `device=` is itself a device buffer allocation. A reader implementing this code as written will reproduce the original trace bug in a different form.
   Fix: The intermediate `cos_device` buffer must also be pre-allocated before the capture bracket and reused on every forward call, or the gather-and-upload must be done entirely outside the trace (e.g., in the decode loop before `ttnn.begin_trace_capture`). Only `ttnn.copy` into `self.cos_replicated` — using an already-device-resident source that was itself pre-allocated — is trace-safe inside the bracket.
