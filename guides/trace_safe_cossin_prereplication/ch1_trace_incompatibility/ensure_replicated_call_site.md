# The `_ensure_replicated` Call Site

This file locates the exact point in `TTNNQwen3FullAttention.forward` where `_ensure_replicated` is called, explains the original sharding bug it was introduced to fix, shows how its fix mechanism — a conditional `ttnn.from_torch` — breaks Metal Trace, and states the corrected design required to make the forward pass trace-safe.

---

## Where `_ensure_replicated` Is Called

Inside `TTNNQwen3FullAttention.forward`, the cos/sin position embedding tensors arrive as arguments and are conditioned before being passed to `ttnn.experimental.rotary_embedding`. The call happens at the top of the forward pass, before any attention computation:

```python
def forward(
    self,
    hidden_states: ttnn.Tensor,
    cos: ttnn.Tensor,          # position embedding cosines
    sin: ttnn.Tensor,          # position embedding sines
    ...
) -> ttnn.Tensor:

    # Ensure cos/sin are replicated across all mesh devices before use.
    # why: rotary_embedding requires the full frequency table on each device;
    #      TP sharding would give each device only a slice of the table.
    cos = self._ensure_replicated(cos)
    sin = self._ensure_replicated(sin)

    # All subsequent ops use the (now replicated) cos and sin tensors.
    hidden_states = ttnn.experimental.rotary_embedding(
        hidden_states, cos, sin, ...
    )
    ...
```

In a `TracedRun` execution, the trace capture bracket wraps the entire `forward` call. The call sequence relative to the bracket is therefore:

```
ttnn.begin_trace_capture(...)          # bracket opens
  │
  ├─ cos = self._ensure_replicated(cos)   <── inside capture
  │    └─ ttnn.from_torch(cos_torch, device=mesh_device)  (if sharded)
  │         └─ allocates NEW device buffer  <── BREAKS TRACE
  │
  ├─ sin = self._ensure_replicated(sin)   <── inside capture
  │    └─ ttnn.from_torch(sin_torch, device=mesh_device)  (if sharded)
  │         └─ allocates NEW device buffer  <── BREAKS TRACE
  │
  └─ ttnn.experimental.rotary_embedding(...)
ttnn.end_trace_capture(...)            # bracket closes
```

---

## The Original Bug `_ensure_replicated` Was Solving

Qwen3 uses tensor parallelism (TP) to distribute the attention computation across multiple devices. When cos/sin tensors are generated by the embedding layer, they may be produced with a TP-sharded memory configuration: each device in the mesh holds a contiguous slice of the frequency table along the head-dimension axis rather than the full table.

`ttnn.experimental.rotary_embedding` applies the rotation:

$$q'_{2k} = q_{2k}\cos(\theta_k) - q_{2k+1}\sin(\theta_k)$$

for each consecutive pair index $k$ (Qwen3 uses the consecutive-pairs convention, also called Llama-style, where adjacent elements $q_{2k}$ and $q_{2k+1}$ are paired rather than the GPT-NeoX half-rotation pairing). This requires the kernel on each device to access $\cos(\theta_k)$ and $\sin(\theta_k)$ for the full range of $k$ values assigned to that device's query and key heads. If the cos/sin table is sharded, a device holding heads $[h_0, h_1)$ may not have the frequency entries for all positions those heads need. The kernel either silently reads zeros from out-of-bounds memory or raises a shape mismatch error.

`_ensure_replicated` was introduced to detect this condition and produce a correctly replicated cos/sin tensor:

```python
def _ensure_replicated(self, tensor: ttnn.Tensor) -> ttnn.Tensor:
    mem_cfg = tensor.memory_config()

    if mem_cfg.is_sharded():
        # Tensor is TP-sharded. Reconstruct a full replicated copy.
        # why: gather the shards back to host, then re-upload replicated.
        tensor_torch = ttnn.to_torch(
            tensor,
            mesh_composer=ConcatMeshToTensor(self.mesh_device, dim=-1),
        )
        tensor = ttnn.from_torch(
            tensor_torch,
            dtype=tensor.dtype,
            layout=tensor.layout,
            device=self.mesh_device,
            # why: ReplicateTensorToMesh places the full tensor on every device
            mesh_mapper=ReplicateTensorToMesh(self.mesh_device),
            memory_config=self.cos_sin_memory_config,
        )
        # why: ttnn.from_torch allocates a NEW device buffer here;
        #      this is the allocation that breaks trace

    return tensor
```

The logic is correct for non-traced execution. The problem is that `ttnn.from_torch` on the last line allocates a new device buffer on every call, which — as established in [`from_torch_is_a_host_operation.md`](./from_torch_is_a_host_operation.md) — is incompatible with Metal Trace when called inside the capture bracket.

> **Note:** During replay, the Metal runtime re-issues the recorded command buffer directly — Python is never re-executed, and `_ensure_replicated` is never called again. The failure mode is therefore not about conditionality: when `ttnn.from_torch` runs during capture, the address of the newly allocated device buffer is baked into the command buffer as the DMA/kernel-dispatch destination. Between capture and replay that transient buffer may be freed or reused. On replay, the command buffer references a stale address that no longer points to valid data. Python's conditionality is irrelevant because Python does not run at all during replay; the problem is purely that a transient, short-lived buffer address was recorded at capture time.

## The Fix Required

The fix has two parts that together restore the buffer address stability invariant:

**Part 1: Pre-allocate the replicated cos/sin buffers before the trace bracket.**

At model initialisation (or at the start of the decode loop, before `ttnn.begin_trace_capture`), allocate persistent device buffers that will hold the replicated cos and sin tensors:

```python
# Called once, BEFORE ttnn.begin_trace_capture
# why: establish stable device buffer addresses that persist for all replays
self.cos_replicated = ttnn.zeros(
    shape=expected_cos_shape,
    dtype=cos_dtype,
    layout=cos_layout,
    device=self.mesh_device,
    memory_config=replicated_memory_config,  # ReplicateTensorToMesh
)
self.sin_replicated = ttnn.zeros(
    shape=expected_sin_shape,
    dtype=sin_dtype,
    layout=sin_layout,
    device=self.mesh_device,
    memory_config=replicated_memory_config,
)
```

**Part 2: Replace `ttnn.from_torch` inside the forward pass with `ttnn.copy` into the pre-allocated buffers.**

Inside `forward` (and therefore inside the capture bracket), instead of allocating new buffers, copy the replicated data into the buffers whose addresses are already stable:

```python
def forward(self, hidden_states, cos, sin, ...):

    # cos and sin must arrive as device-resident tensors whose buffer
    # addresses are already stable (i.e. allocated before the trace
    # capture bracket opened).  See Note below.
    ttnn.copy(cos, self.cos_replicated)
    ttnn.copy(sin, self.sin_replicated)
    cos = self.cos_replicated
    sin = self.sin_replicated

    hidden_states = ttnn.experimental.rotary_embedding(
        hidden_states, cos, sin, ...
    )
```

> **Note:** The caller (the decode loop) is responsible for ensuring `cos` and `sin` are already device-resident before passing them into `forward`. Any host-to-device transfer (e.g. `ttnn.from_torch`) and any shard-gather-then-replicate work must happen in the decode loop *before* `ttnn.begin_trace_capture`. Passing a freshly allocated device tensor — one created inside the capture bracket — is the same class of bug as the original `_ensure_replicated` allocation and will break the trace for the same reason.

> **Option B (alternative):** If the caller cannot guarantee a device-resident input, perform the `ttnn.from_torch` call entirely outside the trace bracket (in the decode loop, before `ttnn.begin_trace_capture`), store the result in a module-level device tensor, and pass that tensor into `forward`. Inside `forward`, only `ttnn.copy` is then used. This is semantically identical to Option A and has the same stability guarantee.

For the trace-safe/unsafe principle, see [from_torch_is_a_host_operation.md](./from_torch_is_a_host_operation.md).
