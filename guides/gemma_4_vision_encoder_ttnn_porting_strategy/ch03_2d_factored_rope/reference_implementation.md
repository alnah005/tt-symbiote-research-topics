# Reference Implementation

This file walks through the HuggingFace Transformers implementation of 2D factored RoPE for the Gemma 4 vision encoder. All code references are from `transformers/models/gemma4/modeling_gemma4.py` and `modular_gemma4.py`.

## Overview of the Data Flow

The 2D RoPE pipeline has three stages:

1. **Position ID generation** (image processor) — Convert patch grid dimensions to `(x, y)` coordinate pairs
2. **Frequency table computation** (`Gemma4VisionRotaryEmbedding.forward`) — Compute per-patch cos/sin tables from position IDs
3. **Rotation application** (`apply_multidimensional_rope`) — Split Q/K, apply standard RoPE to each half, concatenate

```
Image Processor          Gemma4VisionRotaryEmbedding          Gemma4VisionAttention
     |                            |                                    |
     | pixel_position_ids         |                                    |
     | [B, L, 2]                  |                                    |
     +--------------------------->|                                    |
                                  | cos [B, L, 72]                     |
                                  | sin [B, L, 72]                     |
                                  +---------------------------------->|
                                                                      | apply_multidimensional_rope(Q, cos, sin, pos_ids)
                                                                      | apply_multidimensional_rope(K, cos, sin, pos_ids)
                                                                      |
                                                                      V
                                                             Rotated Q, K [B, L, H, 72]
```

## Stage 1: Position ID Computation

Position IDs are generated by the image processor, not the model itself. The logic is:

```python
# Given an image resized to (H, W) where H and W are divisible by patch_size=16
patch_height = H // patch_size  # e.g., 480 // 16 = 30
patch_width  = W // patch_size  # e.g., 448 // 16 = 28

# Generate 2D grid coordinates
patch_grid = torch.meshgrid(
    torch.arange(patch_width),   # x: 0, 1, ..., 27
    torch.arange(patch_height),  # y: 0, 1, ..., 29
    indexing="xy",
)
# patch_grid[0] has shape [patch_height, patch_width] — x-coordinates
# patch_grid[1] has shape [patch_height, patch_width] — y-coordinates

stacked_grid = torch.stack(patch_grid, dim=-1)  # [patch_height, patch_width, 2]
pixel_position_ids = stacked_grid.reshape(-1, 2)  # [num_patches, 2]
```

For a 480x448 image with `patch_size=16`:
- `patch_height = 30`, `patch_width = 28`
- `num_patches = 30 * 28 = 840`
- `pixel_position_ids` shape: `[840, 2]`
- x-coordinates range: 0 to 27
- y-coordinates range: 0 to 29

> **Tip:** The `indexing="xy"` parameter in `torch.meshgrid` is critical. With `"xy"` indexing, the first output tensor varies along columns (x-axis) and the second varies along rows (y-axis). This matches the convention that position_ids[:, 0] is x and position_ids[:, 1] is y. Using the default `"ij"` indexing would swap x and y.

For batched inputs, position IDs are padded to the maximum sequence length in the batch:

```python
# Padded to max_patches with -1 for padding positions
# pixel_position_ids: [batch, max_patches, 2]
# Padding positions have coordinates (-1, -1)
```

> **Warning:** Padding coordinates of `(-1, -1)` produce non-zero rotation angles. The attention mask must ensure that padding positions do not contribute to attention scores. If padding positions leak into the attention computation, they will produce incorrect rotated Q/K values.

## Stage 2: Gemma4VisionRotaryEmbedding

This module computes the cos and sin tables from position IDs. It inherits from `LlamaRotaryEmbedding` but overrides the frequency computation.

### Initialization: compute_default_rope_parameters

```python
@staticmethod
def compute_default_rope_parameters(
    config: Gemma4VisionConfig | None = None,
    device: torch.device | None = None,
    seq_len: int | None = None,
) -> tuple[torch.Tensor, float]:
    base = config.rope_parameters["rope_theta"]      # 100.0
    dim = getattr(config, "head_dim", None) \
          or config.hidden_size // config.num_attention_heads  # 72

    # KEY: spatial_dim = head_dim // 2 = 36
    # Frequencies are computed over the PARTITIONED dimension,
    # not the full head_dim. Both x and y axes share the same
    # frequency table.
    spatial_dim = dim // 2  # 36

    attention_factor = 1.0  # No post-scaling
    inv_freq = 1.0 / (
        base ** (
            torch.arange(0, spatial_dim, 2, dtype=torch.int64)
            .to(device=device, dtype=torch.float)
            / spatial_dim
        )
    )
    # inv_freq shape: [18]
    # inv_freq[i] = 1 / (100 ^ (2i / 36))  for i = 0..17
    return inv_freq, attention_factor
```

Key observations:

1. **`spatial_dim = dim // 2 = 36`** — The frequency table is computed for half the head dimension, not the full 72. This is the "factored" part: each spatial axis gets its own independent set of 18 frequency pairs.

2. **`arange(0, spatial_dim, 2)`** generates `[0, 2, 4, ..., 34]` — 18 values. So `inv_freq` has 18 entries.

3. **Division by `spatial_dim` (36)**, not `dim` (72). This is critical: it ensures the frequency spectrum spans the full range for each spatial axis independently.

4. **`attention_factor = 1.0`** — No additional scaling is applied. The `attention_scaling` multiplier in the forward pass is effectively 1.0.

### Forward: Computing cos/sin for 2D Positions

```python
@torch.no_grad()
def forward(self, x, position_ids):
    # x: hidden states, used only for dtype/device
    # position_ids: [batch, num_patches, 2] — (x, y) coordinates

    # inv_freq: [18] -> expand to [batch, 18, 1]
    inv_freq_expanded = self.inv_freq[None, :, None].float() \
        .expand(position_ids.shape[0], -1, 1).to(x.device)

    all_cos, all_sin = [], []
    for i in range(2):  # i=0: x-axis, i=1: y-axis
        # Extract positions for this spatial dimension
        dim_position_ids = position_ids[:, :, i]          # [batch, num_patches]
        dim_position_ids_expanded = dim_position_ids[:, None, :].float()
                                                           # [batch, 1, num_patches]

        # Compute frequencies: outer product of inv_freq and positions
        # [batch, 18, 1] @ [batch, 1, num_patches] -> [batch, 18, num_patches]
        freqs = (inv_freq_expanded.float() @ dim_position_ids_expanded.float())
        freqs = freqs.transpose(1, 2)                     # [batch, num_patches, 18]

        # Double the frequencies for rotate_half: [batch, num_patches, 36]
        emb = torch.cat((freqs, freqs), dim=-1)

        cos = emb.cos() * self.attention_scaling           # [batch, num_patches, 36]
        sin = emb.sin() * self.attention_scaling           # [batch, num_patches, 36]

        all_cos.append(cos)
        all_sin.append(sin)

    # Concatenate x and y cos/sin along the last dimension
    cos = torch.cat(all_cos, dim=-1).to(dtype=x.dtype)    # [batch, num_patches, 72]
    sin = torch.cat(all_sin, dim=-1).to(dtype=x.dtype)    # [batch, num_patches, 72]
    return cos, sin
```

Step-by-step for a single batch element with 840 patches (480x448 image):

| Step | Operation | Shape |
|------|-----------|-------|
| Input `position_ids` | Grid coordinates | `[1, 840, 2]` |
| Extract x-coords | `position_ids[:, :, 0]` | `[1, 840]` |
| Outer product | `inv_freq @ x_coords` | `[1, 18, 840]` |
| Transpose | Move patch dim to position 1 | `[1, 840, 18]` |
| Double | `cat(freqs, freqs)` | `[1, 840, 36]` |
| cos/sin | Element-wise trig | `[1, 840, 36]` each |
| (Repeat for y-coords) | | `[1, 840, 36]` each |
| Final concat | `cat(cos_x, cos_y)` | `[1, 840, 72]` |

> **Tip:** The `cat(freqs, freqs)` doubling is required by the `rotate_half` implementation. In `rotate_half`, the input is split in half and the halves are swapped with a sign flip. The doubled frequencies ensure that element $j$ and element $j + d_s/2$ in the rotation vector have the same frequency, matching the pairing structure of `rotate_half`.

### Numerical Example

For a patch at grid position $(x, y) = (5, 12)$:

```python
# inv_freq for first 4 entries:
# i=0: 1 / 100^(0/36)   = 1.000
# i=1: 1 / 100^(2/36)   = 0.774
# i=2: 1 / 100^(4/36)   = 0.599
# i=3: 1 / 100^(6/36)   = 0.464

# x=5 frequencies:
# freqs_x = [5*1.000, 5*0.774, 5*0.599, 5*0.464, ...]
#          = [5.000,   3.872,   2.997,   2.321,   ...]

# y=12 frequencies:
# freqs_y = [12*1.000, 12*0.774, 12*0.599, 12*0.464, ...]
#          = [12.000,   9.293,   7.192,   5.570,   ...]

# cos_x[0] = cos(5.000) = 0.284
# sin_x[0] = sin(5.000) = -0.959
# cos_y[0] = cos(12.000) = 0.844
# sin_y[0] = sin(12.000) = -0.536
```

These values rotate the first and second halves of the query/key head dimensions by different angles, encoding the patch's horizontal and vertical positions independently.

## Stage 3: apply_multidimensional_rope

This function applies the precomputed cos/sin rotations to the query and key tensors.

```python
def apply_multidimensional_rope(
    x: torch.Tensor,          # [batch, seq, num_heads, head_dim]
    cos: torch.Tensor,        # [batch, seq, head_dim]
    sin: torch.Tensor,        # [batch, seq, head_dim]
    position_ids: torch.Tensor,  # [batch, seq, 2]
    unsqueeze_dim: int = 2,   # unsqueeze along head dim for broadcasting
) -> torch.Tensor:

    ndim = position_ids.shape[-1]              # 2 (number of spatial dims)
    num_input_channels = x.shape[-1]           # 72 (head_dim)

    # How many channels to rotate per spatial dimension
    num_rotated_channels_per_dim = 2 * (num_input_channels // (2 * ndim))
    # = 2 * (72 // (2 * 2)) = 2 * 18 = 36

    # Split x, cos, sin into ndim=2 chunks of 36 each
    split_sizes = [num_rotated_channels_per_dim] * ndim    # [36, 36]
    x_parts = torch.split(x, split_sizes, dim=-1)         # 2 tensors of [..., 36]
    cos_parts = torch.split(cos, split_sizes, dim=-1)      # 2 tensors of [..., 36]
    sin_parts = torch.split(sin, split_sizes, dim=-1)      # 2 tensors of [..., 36]

    # Apply standard 1D RoPE to each chunk independently
    y_parts = [
        apply_rotary_pos_emb(
            x=x_parts[k],
            cos=cos_parts[k],
            sin=sin_parts[k],
            unsqueeze_dim=unsqueeze_dim,  # broadcasts cos/sin to num_heads dim
        )
        for k in range(ndim)
    ]

    # Concatenate back to full head_dim
    return torch.cat(y_parts, dim=-1)          # [..., 72]
```

The inner `apply_rotary_pos_emb` function is the standard rotate_half implementation:

```python
def rotate_half(x):
    """Rotates half the hidden dims of the input."""
    x1 = x[..., : x.shape[-1] // 2]     # first 18 dims
    x2 = x[..., x.shape[-1] // 2 :]     # last 18 dims
    return torch.cat((-x2, x1), dim=-1)  # [-x2, x1]

def apply_rotary_pos_emb(x, cos, sin, unsqueeze_dim=1):
    cos = cos.unsqueeze(unsqueeze_dim)   # broadcast to num_heads
    sin = sin.unsqueeze(unsqueeze_dim)
    return (x * cos) + (rotate_half(x) * sin)
```

### Dimensional Breakdown

For a single patch with `head_dim=72`:

```
x (query/key head):  [q_0, q_1, ..., q_35 | q_36, q_37, ..., q_71]
                      <---- x-axis ---->   <---- y-axis ---->

cos:                 [cos_x_0, ..., cos_x_35 | cos_y_0, ..., cos_y_35]
sin:                 [sin_x_0, ..., sin_x_35 | sin_y_0, ..., sin_y_35]

After split:
  x_parts[0] = [q_0, ..., q_35]     cos_parts[0] = [cos_x_0, ..., cos_x_35]
  x_parts[1] = [q_36, ..., q_71]    cos_parts[1] = [cos_y_0, ..., cos_y_35]

After apply_rotary_pos_emb to each part:
  y_parts[0] = RoPE_1D(x_parts[0], cos_x, sin_x)   — x-position encoded
  y_parts[1] = RoPE_1D(x_parts[1], cos_y, sin_y)   — y-position encoded

After concat:
  output = [y_parts[0] | y_parts[1]]                — full 2D position encoded
```

### Where It Is Called

In `Gemma4VisionAttention.forward`, after projection and per-head normalization:

```python
# Q path
query_states = self.q_proj(hidden_states).view(hidden_shape)  # [B, L, H, 72]
query_states = self.q_norm(query_states)                       # per-head RMSNorm
query_states = apply_multidimensional_rope(                    # 2D RoPE
    query_states, cos, sin, position_ids
)
query_states = query_states.transpose(1, 2)                    # [B, H, L, 72]

# K path (identical)
key_states = self.k_proj(hidden_states).view(hidden_shape)
key_states = self.k_norm(key_states)
key_states = apply_multidimensional_rope(
    key_states, cos, sin, position_ids
)
key_states = key_states.transpose(1, 2)

# V path — NO RoPE, only normalization (without learned scale)
value_states = self.v_proj(hidden_states).view(hidden_shape)
value_states = self.v_norm(value_states)                       # no scale parameter
value_states = value_states.transpose(1, 2)
```

> **Warning:** RoPE is applied to Q and K only, not V. The value path has RMSNorm but no rotary embedding. This is consistent with the RoPE design principle: rotary embeddings modulate the dot-product attention scores (which depend on Q and K), not the values being aggregated.

## Key Numerical Properties

### cos/sin Table Characteristics

For a typical 280-token budget (840 patches, ~30x28 grid):

| Property | Value |
|----------|-------|
| cos/sin shape | `[batch, 840, 72]` |
| cos value range | `[-1.0, 1.0]` |
| sin value range | `[-1.0, 1.0]` |
| cos mean (approx.) | Near 0 (balanced rotations across the grid) |
| Number of unique cos/sin rows | 840 (one per patch; all are distinct for non-padding patches) |
| Memory per table (BF16) | $840 \times 72 \times 2 = 121$ KB |
| Total cos + sin (BF16) | $\approx 242$ KB |

### Computation Cost

| Operation | FLOPs per call |
|-----------|---------------|
| `inv_freq @ position_ids` (outer product) | $2 \times B \times 18 \times L$ |
| `cos`/`sin` (transcendental) | $2 \times 2 \times B \times L \times 36$ |
| `rotate_half` + element-wise ops in apply | $2 \times 4 \times B \times L \times H \times 36$ |

For `B=1, L=840, H=16`: the apply step costs $\sim 4 \times 840 \times 16 \times 36 \times 2 \approx 3.9$M FLOPs per Q or K, which is negligible compared to the projection matmuls ($\sim 2 \times 840 \times 1152 \times 1152 \approx 2.2$B FLOPs for Q projection alone).

> **Tip:** The cos/sin tables are computed once per forward pass by `Gemma4VisionRotaryEmbedding` and reused across all 27 encoder layers. The `position_embeddings = (cos, sin)` tuple is passed through the encoder stack. There is no per-layer recomputation.

## Summary

The reference implementation follows a clean three-stage pattern:

1. **Position IDs**: The image processor generates `[batch, num_patches, 2]` grid coordinates using `meshgrid` with `"xy"` indexing.
2. **Cos/Sin tables**: `Gemma4VisionRotaryEmbedding.forward` loops over the 2 spatial dimensions, computes `inv_freq @ positions` for each, takes cos/sin, and concatenates to `[batch, num_patches, 72]`.
3. **Application**: `apply_multidimensional_rope` splits Q/K along the head dimension into two 36-element chunks, applies standard `rotate_half` RoPE to each chunk, and concatenates back to 72.

This implementation is numerically simple but requires the head dimension split and 2D position handling that current TTNN RoPE kernels do not natively support. The next file analyzes these gaps in detail.
